# Data Dictionary

This data dictionary documents the expected fields and concepts used in the SpaceX Falcon 9 landing prediction workflow. Exact column names may differ slightly across the preserved lab notebooks, API extracts, and cleaned modeling tables; this document defines the intended analytical contract.

## Core Modeling Fields

| Field | Type | Source | Nullable | Role | Description |
| --- | --- | --- | --- | --- | --- |
| `landing_success` | binary | Lab-derived outcome | no | Target | Whether the first stage landed successfully. |
| `class` | binary | Original capstone notebooks | no | Target alias | Common lab target alias for landing success. |
| `flight_number` | integer | SpaceX API/lab | no | Feature | Sequential launch number or launch ordering variable. |
| `date_utc` | datetime/string | SpaceX API | yes | Feature source | Launch timestamp used for derived date features. |
| `launch_date` | datetime/string | Lab data | yes | Feature source | Alternate launch date field used in examples. |
| `payload_mass_kg` | numeric | SpaceX API/lab | yes | Feature | Payload mass in kilograms. |
| `orbit` | categorical | SpaceX API/lab | yes | Feature | Target orbit category. |
| `launch_site` | categorical | SpaceX API/lab | yes | Feature | Launch site identifier or label. |
| `site_name` | categorical | Refactored examples | yes | Feature | Human-readable launch site field used by helper examples. |
| `booster_version` | categorical | SpaceX API/lab | yes | Feature | Booster or rocket version used for launch. |
| `gridfins` | boolean | SpaceX API/lab | yes | Feature | Whether grid fins were used. |
| `reused` | boolean | SpaceX API/lab | yes | Feature | Whether the booster/core had been reused. |
| `legs` | boolean | SpaceX API/lab | yes | Feature | Whether landing legs were present. |
| `landing_pad` | categorical | SpaceX API/lab | yes | Feature | Landing pad identifier when available. |

## Engineered Fields

| Field Pattern | Type | Created By | Description |
| --- | --- | --- | --- |
| `{date_column}_year` | integer | `create_datetime_features` | Launch year. |
| `{date_column}_month` | integer | `create_datetime_features` | Launch month. |
| `{date_column}_day` | integer | `create_datetime_features` | Day of month. |
| `{date_column}_dayofweek` | integer | `create_datetime_features` | Day of week, where Monday is 0. |
| `{date_column}_quarter` | integer | `create_datetime_features` | Calendar quarter. |
| `{feature_a}_x_{feature_b}` | numeric | `create_interaction_features` | Multiplicative interaction between two numeric features. |
| Polynomial feature names | numeric | `create_polynomial_features` | Polynomial expansion generated by scikit-learn. |
| One-hot encoded columns | binary | `encode_categorical(..., method="onehot")` | Indicator columns generated from categorical values. |
| Label encoded columns | integer | `encode_categorical(..., method="label")` | Integer-coded category values. |

## Data Quality Expectations

Before modeling, the dataset should satisfy these expectations:

- The target column is present and binary.
- Feature columns do not include the target.
- Numeric fields used for modeling are numeric after cleaning.
- Categorical fields are encoded before model fitting.
- Payload mass values are non-negative when present.
- Missing values are handled consistently before model training.
- Date features are derived from parseable date columns.

## Notes for Reviewers

- The original notebooks may use different casing or field names from the refactored examples.
- `landing_success` and `class` should be treated as target aliases, not simultaneous independent features.
- Public SpaceX/lab data can be incomplete. Missingness should be documented rather than silently ignored.
- Any final model report should list the exact feature columns used in the selected model.
